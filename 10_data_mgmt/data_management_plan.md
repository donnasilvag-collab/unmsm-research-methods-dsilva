# Data management plan

## 10.1. Purpose and status

This plan governs the data created or used in the study, *Influence of information security risk management on the effectiveness of access control, source code protection, and software development traceability in Peruvian companies: protocol for a mixed methods study*. It complements the research protocol in `03_protocol/` and the ethics protocol in `09_ethics/`.

The project currently has one active data component: a bounded public benchmark of 48 GitHub repositories documented in `05_pipeline/`. The survey, interviews, and authorized organizational-document review described in the research protocol are future components. No fieldwork data, personal data, confidential documents, proprietary source code, credentials, or incident records are stored in this public repository.

This is a living plan. It must be reviewed before recruitment, before a new digital service processes fieldwork data, and before any result or derived dataset is shared outside the research team.

## 10.2. Data inventory and classification

| Data asset | Status and contents | Classification | Location and sharing rule |
| --- | --- | --- | --- |
| Public repository benchmark | Public GitHub repository and organization metadata, observable workflow and history signals, and available OpenSSF Scorecard responses for 48 repositories. | Public research data. | Source workbook in `05_pipeline/data/raw/`; scripts and approved derived outputs in `05_pipeline/`. Public release is limited to the documented benchmark and its provenance. |
| Benchmark derivatives | Validated CSV, descriptive summaries, bootstrap outputs, parameters, and experiment artifacts generated by the pipeline. | Public research outputs. | Generated through the versioned pipeline. They may be shared with the methods, assumptions, and limits recorded in the repository. |

It may contain personal and organizationally sensitive information. | Will be stored outside GitHub in protected, access-controlled storage confirmed before recruitment. Only de-identified, approved aggregates may be released. |
| Interview recordings and transcripts | Planned semistructured interview material from voluntary key informants. | Restricted research data with possible direct and indirect identifiers. | Will be stored outside GitHub. Raw recordings and unredacted transcripts will never be published in this repository. |

| Authorized organizational documents | Planned non-confidential or redacted policies, procedures, or evidence voluntarily provided within an agreed scope. | Restricted organizational data. | Will remain outside GitHub unless an item is explicitly cleared for public release. |

The public benchmark and the planned fieldwork are separate data streams. A public repository URL, organization name, or benchmark score will not be used to identify, recruit, profile, or evaluate an individual participant. Confidential fieldwork records will not be merged with public benchmark records without a revised protocol, a documented justification, and the required authorization.

## 10.3. Collection and documentation

The public benchmark is a dated snapshot extracted on 31 July 2026. The source workbook records public provenance fields, collection dates, public endpoints, and validation details. Each row represents one repository, not one company or one person. The data dictionary in the workbook and the documentation in `05_pipeline/` describe the public indicators and the four composite observability proxies.

Before fieldwork begins, the survey instrument, interview guide, consent materials, codebook, and recruitment procedure will be versioned as controlled research documents. The instrument will collect only information needed to answer the research questions. It will not request passwords, access tokens, proprietary source code, private repository addresses, vulnerability details, or incident evidence.

If contact information is needed to schedule an interview, it will be collected separately from the survey and analytical data. Interview transcripts will use participant and organization codes. The coding scheme, transformation steps, software versions, and analytical decisions will be documented so that approved derived results can be traced to their source without exposing identifying material.

## 10.4. FAIR and documentation approach

The project applies the FAIR principles in a proportionate way. FAIR does not require all research data to be open. A restricted resource can still be findable and well documented while its contents remain protected.

| FAIR principle | Public benchmark implementation | Planned fieldwork implementation |
| --- | --- | --- |
| Findable | The repository contains the source path, documentation, provenance fields, and version history for the public benchmark. | The researcher will maintain an internal inventory of data assets, versions, and responsible roles. Restricted data will not be indexed publicly. |
| Accessible | Public materials are available through the repository and can be regenerated through the documented pipeline. | Access will be limited to approved roles. The plan will describe how an authorized academic reviewer may request access when a legitimate review need exists. |
| Interoperable | The pipeline uses documented, machine-readable formats where appropriate, including CSV, YAML, and Markdown. | Survey exports, codebooks, and derived tables will use documented formats and clear field definitions where the approved storage environment permits. |
| Reusable | The datasheet, model card, pipeline README, parameters, and provenance fields state appropriate uses and limits. | Only de-identified outputs cleared through the ethics and review process may be shared. Their documentation will state scope, transformations, limitations, and access conditions. |

Every shareable data release must include a README or equivalent documentation that states its purpose, source, structure, date or version, field definitions, processing steps, known limits, and conditions of use. The public benchmark already has a datasheet in `07_model_card/datasheet.md`.

## 10.5. Storage, access, and security controls

The public benchmark is intentionally limited to public information and is versioned in the repository with its scripts and documentation. The small source workbook is tracked by Git; the derived analysis-ready CSV is a DVC output that can be rebuilt with `dvc repro`. The repository's ignore rules exclude local environments, caches, local MLflow runs, generated temporary files, and sensitive environment files.

Fieldwork storage will be selected before recruitment in accordance with the applicable institutional requirements. It must provide protected, access-controlled storage separate from the public repository. The setup will document the responsible account, storage region, access roles, backup approach, and recovery procedure. Credentials, keys, and participant identifiers will not be committed to Git or shared through public issues, notebooks, or chat messages.

Access will follow the principle of least privilege. Identifiable fieldwork records will be available only to the researcher and to authorized academic supervisors or reviewers when the applicable process requires their access. Permission reviews will occur when a person joins or leaves the authorized group and before material is transferred to another environment.

## 10.6. Privacy protection and disclosure review

The study will protect personal and organizational confidentiality through minimization, separation of identifiers, de-identification, and review before dissemination. Removing names alone is insufficient when a combination of role, company characteristics, technology details, location, and quoted events could identify a participant or organization.

Before a table, quotation, codebook, or derived dataset is shared, the researcher will review it for direct identifiers, quasi-identifiers, sensitive free text, and contextual combinations that could permit re-identification. The available actions are aggregation, generalization, redaction, suppression, or withholding the material from release. The choice and its residual risk will be recorded with the output.

The public benchmark does not contain participant records, but it can still lead to unfair reputational inference if its observable proxies are presented as a complete security assessment. Results must remain descriptive and repository-level. Missing public signals mean "not observed" and must not be treated as evidence that an internal control is absent.

## 10.7. Versioning, quality, and reproducibility

Git versions the public workbook, scripts, parameters, documentation, and approved output definitions. DVC defines the derivation of the analysis-ready benchmark CSV. MLflow records the seeded local experiment runs when the pipeline is executed, and Docker specifies an isolated execution environment. These controls make the public demonstration inspectable without exposing fieldwork material.

For planned fieldwork, the researcher will retain an immutable original export where the approved storage environment permits it, then create documented working copies for cleaning, coding, and analysis. Each transformation will have a date, a responsible role, an input version, an output version, and a short explanation. Corrections to collected data will preserve an audit trail rather than silently replacing a prior value.

Quality checks will include instrument validation before deployment, permitted-value checks, duplicate and missing-data review, codebook consistency checks, and review of de-identification before release. The purpose of a quality check is to identify a problem in the data or process. It does not convert an observable public proxy into a direct measure of an organization's internal security practice.

## 10.8. Sharing and access decisions

| Material | Sharing decision |
| --- | --- |
| Public benchmark source workbook, scripts, parameters, and approved results | Public in this repository, with provenance and limitations retained. Reusers must respect the terms that apply to the underlying public sources. |
| Raw survey responses, interview recordings, unredacted transcripts, contact details, linkage files, and confidential organizational documents | Not public. They remain in restricted storage and are not placed in Git, DVC remotes, issue trackers, or public cloud folders. |
| De-identified survey aggregates, disclosure-reviewed quotations, codebooks, and analytical scripts | May be shared only after the ethics and institutional requirements are met and the disclosure review confirms that the release is appropriate. |
| Final thesis documentation | Public only to the extent that it contains approved, non-sensitive methods, code, documentation, and derived findings. |

No release will imply that a participant, team, or organization endorses the research conclusions. The study is not an audit, certification, or comparative ranking of organizations.

## 10.9. Retention, disposal, and preservation

The public benchmark will remain as a dated, versioned course artifact. A future refresh must preserve the prior version, record the new extraction date, document any changed sampling or indicator rule, and avoid unqualified comparisons across snapshots.

The retention period for fieldwork data has not yet been set because recruitment and institutional review have not begun. Before collection, the research team will record the retention period, the deletion or de-identification method, the responsible role, and any archival requirement imposed by the relevant institution. At the end of that period, direct identifiers and linkage files will be securely deleted or irreversibly de-identified. Approved, non-sensitive documentation and reproducibility materials may be preserved as part of the academic record.

## 10.10. Incident response

Any suspected loss, unauthorized access, accidental disclosure, or inappropriate transfer of restricted data will be documented and reported through the applicable institutional route. The immediate priority is to contain the exposure by restricting access, preserving the information needed to understand what occurred, and avoiding further dissemination.

Before fieldwork begins, the researcher will define contact roles for incident escalation, an internal record of the event, the decision process for notifying affected participants or authorities when required, and the corrective action taken. The applicable legal and institutional obligations will be confirmed for the specific data, location, and incident before a response is finalized.

## 10.11. Roles, review, and decision log

Donna Silva is responsible for maintaining this plan, documenting changes to the data lifecycle, and ensuring that public repository materials remain within the stated scope. Academic supervisors or authorized institutional reviewers may review restricted material only when the approved process requires it.

The decision log for fieldwork will record material changes to collection instruments, storage location, access roles, external processors, de-identification approach, retention, or sharing. Each entry will state the date, change, reason, responsible person, and whether additional ethics or institutional review was required.

The plan will be reviewed at these points:

- before recruitment and collection of non-public data;
- before using a new cloud, transcription, coding, or AI-enabled service with fieldwork material;
- before releasing a derived dataset, quotation, or result that could create disclosure risk;
- at project closure, when retention, deletion, and preservation decisions are implemented.

## 10.12. Pre-collection checklist

| Check | Required evidence before fieldwork |
| --- | --- |
| Research and ethics requirements are confirmed. | Approved or documented institutional route, finalized consent materials, and approved instruments. |
| The collection is limited to necessary variables. | Variable inventory, codebook, and explicit exclusion of credentials, proprietary code, and incident evidence. |
| Protected storage is ready. | Documented location, access roles, backup and recovery process, and separation of identifiers from responses. |
| Data handling is traceable. | Versioning method, transformation log, quality-check plan, and disclosure-review procedure. |
| Any external processor is assessed. | Documented data flow, approved use conditions, and participant information where required. |
| Retention and incident roles are assigned. | Retention schedule, secure disposal method, escalation contacts, and incident record template. |
